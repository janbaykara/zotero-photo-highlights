# Zotero Photo Highlights

The plugin turns photos of physical pages into Zotero highlight annotations. User steps are in [README.md](../README.md).

## Wizard

`openPhotoToAnnotationDialog` mounts a Preact dialog (`openPreactDialog`, about 900×640) with internal steps: add photos, link each photo to a book, mark the passages, review decisions, summary.

Entry points are the item context menu and the Tools menu. The item menu locks every photo to that book and skips the link step. The Tools menu still asks which book each photo belongs to. An attachment selection resolves to its parent.

Cancel before review writes nothing and deletes temp files. Highlights already created during review stay. Review walks the passages that still need a decision, with that highlight’s place in the queue and a status for a duplicate, several locations, or text that was not found. Several locations ask you to choose where to locate the passage, and explain that it appears in more than one place. They are a two-column list. Each option grows to show the words before and after the passage and, for a PDF, whether the hit is near the top, middle, or bottom of the page. A click selects one. Save writes the highlight and stays unavailable until a place is chosen. Edit quote, add a comment, and choose the passage again sit under the highlighted passage. The quote editor and comment field stay closed until opened. Skip on review skips that passage. The photo file stays until every passage from it is finished, and it is imported at most once.

## Temp files and OCR

Photos are copied under Zotero’s temp directory (`photo-highlights/<session>/`). On upload that copy is rewritten so its pixels are upright: the EXIF orientation tag is applied once and removed. The add step shows the photos in a grid. Each cell is a smaller preview, the name, recognition status with a spinner while it runs, and a remove control. Removing a photo deletes its temp files. Extra quarter-turns are written to a sibling JPEG from the upright copy, then scaled and recognized again. OCR uses a JPEG whose longest side is at most 2400px. A kept photo is the oriented file, including any extra turns, not the camera original. The time shown under each photo comes from exifr (`DateTimeOriginal`, then `CreateDate`, then `ModifyDate`). If the file has no EXIF date, the file’s own creation time is used. That time is written to the highlight as its date added. The highlight’s date modified stays the moment it is saved.

On macOS, `addon/content/ocr/vision-ocr.js` runs under `/usr/bin/osascript` and calls `VNRecognizeTextRequest` (accurate, language correction on). It tries the preferred language tag even when that tag is absent from Vision’s supported list, then tries again with automatic language detection. A word whose box cannot be read is skipped. A line that has text but no word boxes is split across that line’s rectangle. The JSON is written to stdout and read until the pipe closes, for Apple Vision and for Windows OCR. One read returns only the first chunk, and a full page of boxes does not fit in that chunk, so the rest would be dropped and the JSON would not parse. A parsed success is kept even if the process exit code is non-zero. A failed helper is started once more. On Windows, `addon/content/ocr/windows-ocr.ps1` runs under `powershell.exe -STA` and calls `Windows.Media.Ocr.OcrEngine`. A failure includes the PowerShell exception, and the language that was missing, in the debug log beside the exit code and stderr. Both are started with Firefox `Subprocess`, because `Zotero.Utilities.Internal.exec` does not capture stdout. A packed add-on serves those scripts from inside the XPI, which osascript and PowerShell cannot open, so each script is copied into Zotero’s temp directory (`photo-highlights-ocr/<version>/`) before it is started. If that copy fails, recognition continues without the helper. The helper receives the Tesseract language’s BCP-47 candidates (`zh-Hans` and `zh-Hant` stay distinct; `vie` can match `vi-VT`). An unreadable result or a 45 second timeout falls through after the one retry. The Windows helper exits 2 when that language pack is not installed, and that result is not retried. When the helper is missing or returns no text, PP-OCRv4 mobile runs in the wizard window before Tesseract, including on Linux. `scripts/copy-ort.mjs` copies ONNX Runtime Web 1.16 (`ort.wasm.min.js` and the single-thread SIMD `ort-wasm-simd.wasm`) into `addon/content/ocr/ort/`, and the wizard loads that script. Threads stay at one, because the dialog has no `SharedArrayBuffer`. The shared detector is `multi_PP-OCRv3_det_mobile`. The recognition model follows the language: English, Latin (German, French, Spanish, Italian, Portuguese, Dutch, Polish, Turkish, Vietnamese), Cyrillic (Russian, Ukrainian), Arabic, simplified Chinese, traditional Chinese, Japanese, or Korean. Hebrew has no model and skips straight to Tesseract. Each ONNX file is downloaded on first use into `<profile>/photo-highlights-paddle/` and kept only when its SHA-256 matches the RapidOCR v3.10.0 release. The character dictionary is downloaded beside it. A bad download is deleted. The detector resizes the JPEG so the long side is at most 960px. Each text line is rotate-cropped to a horizontal strip, which handles skew and mild curl, and read by the recognizer. CTC steps become words: split on spaces for Latin, Cyrillic, and Arabic, and one box per character for Chinese, Japanese, and Korean. Those spans are mapped back to axis-aligned rectangles on the scaled JPEG. A download, runtime, or dictionary failure, a 60 second timeout, or a page with no kept words falls through to Tesseract. When recognition finishes, the add step names the engine under the photo, and the mark step names it beside Recognize again: Apple Vision, Windows OCR, PaddleOCR, or Tesseract.

Each word keeps a `line` index. Vision and Windows lines come from the recognizer, in its reading order. Paddle lines are the detector’s text boxes, grouped when they overlap vertically, with words left to right inside a line. Tesseract words are clustered by vertical overlap, then ordered left to right within a line. The mark step follows those line indexes. Vision boxes are normalized from the bottom left and converted to top-left pixels of the scaled JPEG. Windows boxes are already top-left pixels. If the helper’s pixel size differs from the photo, the boxes are scaled to the photo.

Tesseract.js runs in the wizard window when PaddleOCR returns no words. `addon/content/ocr/` ships `tesseract.min.js`, `worker.min.js`, `tesseract-core.wasm.js` (SIMD LSTM build), and English `tessdata_best` (`eng.traineddata`). The worker is started as a ChromeWorker from the chrome URL of `worker.min.js`, and the core is the chrome URL of `tesseract-core.wasm.js`. That name ends in `.js`, so the worker loads that file. A blob URL does not, and Tesseract would request a core file that was never created. Words below a confidence of 45, and tokens that are mostly punctuation, are dropped. After recognition, the scaled JPEG is scanned for pen underlines and for highlighter behind the words. Words that share an OCR line are searched once.

Underlines use the bottoms of those word boxes as a baseline. A strip just under it is thresholded against the paper beside each pixel, for dark, low-chroma pixels, which keeps biro and pencil in shadow. A horizontal close joins short breaks in the stroke, and a horizontal open drops specks and descenders. A connected component in that strip is an underline when it is wider than about one and a half characters, stays thin and even along its length, and does not run up into the letter bodies. A short break in the stroke still counts as one line. The words whose boxes sit on that span become one passage, in yellow. A second stroke on the same printed line becomes another passage. Letter bottoms and specks do not.

Highlighter uses OpenCV.js. Saturation inside the word boxes is compared with the paper on that same line, so cream paper is not treated as a mark. A wash has to be clearly more saturated than that paper and bright enough not to be ink. A horizontal close and open join the wash across letters and drop specks. A word joins when enough of its box is wash. The mean colour of those pixels is snapped to the nearest Zotero highlight colour, and a change of colour starts another passage. A word that is both highlighted and underlined stays with the highlighter passage.

OpenCV.js is copied from `@techstark/opencv-js` into `addon/content/opencv` when the plugin is built or served, and loaded in the wizard window the first time a photo is recognized. It loads when Detect highlights is on. If it fails to load, underlines are still detected. Each photo has two checkboxes on the mark step. Detect underlines and Detect highlights are off by default. Clearing a checkbox removes the passages that scan added. A passage you dragged, typed, recolored, or commented on stays. Checking it again scans the words already recognized.

The photo fills the mark step. The column beside it has a photo heading, an OCR heading, and a Passages heading, with a horizontal rule between each. Under OCR, the engine dropdown sits above Recognize again. While recognition runs that button is disabled and its label is Recognizing text… with a spinner. The engine list stays open during that pass. Choosing another engine drops the pass that is running and starts again. If recognition fails, Copy debug logs copies the helper’s reason, exit code, and output. Detect underlines and Detect highlights sit under the button, smaller, in two columns. Passages sit under their own heading, each in its own color. Dragging through unmarked words adds a passage in yellow. Dragging a word that already belongs to a passage replaces that passage with the run of OCR words from the pointer press to the pointer, in reading order. A word belongs to only one passage. Typing replaces that passage’s quote and clears its word boxes. Add passage creates an empty one. Remove drops one passage. The dropdown shows auto and the engine that automatic recognition used, and can read the photo again with Apple Vision, Windows OCR, PaddleOCR, or Tesseract alone. Rotate and Recognize again clear the passages and run recognition, then detection, again. Rotate writes the quarter-turns to the stored photo first. A photo with no passage is skipped. It is counted as skipped, and the file is deleted rather than imported.

Other languages are downloaded from `tesseract-ocr/tessdata_best` into `<profile>/photo-highlights-tessdata-best/` the first time they are selected. The language pref is `photoAnnotationOcrLang` (default `eng`).

## Matching

Pure functions in `src/match/` normalize case, quotes, dashes, and line-break hyphenation, then score windows with length-normalized edit distance.

- Auto-locate when the best score is at least 0.84 and the runner-up is at least 0.08 worse.
- Ask when two or more candidates are at least 0.72.
- Otherwise the passage is unmatched.

The words OCR read just before and after the selection are compared with the book text beside each hit. A repeated sentence is located when one copy’s surroundings agree and the others do not. The highlight itself stays the selected words. With no surrounding words, the quote score is unchanged.

Clicking Next on a marked photo starts a search for each of its passages immediately. Page text is read once and shared by later passages. Comparisons yield back to the wizard so the next photo can be marked while the search runs. Review waits only for a passage whose search is still going. That screen is titled Matching up highlights. The book title is at the top. Under it, the current passage is shown with its place among the highlights, and a progress bar that advances once per passage. A smaller line under that says what the search is doing for that passage (opening the file, reading a page or section, searching that page, checking for a duplicate, or saving), without its own bar. It is skipped when every search has already finished. The search runs again if the quote, the words around it, or the book changed. A passage that locates on its own is saved then and is not searched again. Saving still uses the colour and comment from that moment.

The search corpus is the full text of every PDF and EPUB attachment, cached for the session. It does not use `.zotero-ft-cache`.

Duplicate detection treats a quote as already highlighted when the normalized strings contain each other and both are at least 8 characters.

## Positions

PDF highlights store `annotationPosition` as `{ pageIndex, rects }` in PDF space (bottom-left origin). `annotationSortIndex` is `page|charOffset|yFromTop`, zero-padded `5|6|5`, matching Zotero Reader. Page labels come from the PDF catalog when it has `/PageLabels`.

EPUB highlights store a FragmentSelector whose `conformsTo` is `http://www.idpf.org/epub/linking/cfi/epub-cfi.html`. The sort index is `sectionIndex|charOffset`, zero-padded `5|8`. Chapter text is read from the EPUB zip. The CFI is epubjs `EpubCFI` for that character range, with spine step `/6/{2*(index+1)}`. If that range cannot be built, the fallback for a plain chapter body is `epubcfi(/6/{spine}!/4/2,/1:start,/1:end)`.

An unlocated highlight is still an annotation on the PDF or EPUB. Its position JSON is `{}`, so Reader does not draw a box. Highlights set `libraryID` from the attachment before save. If the text cannot be found, review shows the photo, when it was taken, and the start of the passage in its highlight colour, with edit quote, add a comment, and choose the passage again under that passage, then the status and the decision. Review can edit the quote and search again, or return to the photo to drag a new passage. Ambiguous hits that land on the same page with the same text are collapsed to one choice.

## Photos

`retainUnmatchedPhotos` (default `false`) imports the temp copy onto the book with `Zotero.Attachments.importFromFile` when a passage is unmatched or skipped from review and that decision asks to keep the photo. The file is imported once, after the last passage from that photo is saved or decided. Matched passages do not keep the photo. The temp files are deleted when that last passage is finished.
